STEP 4 — SECURITY & PRODUCTION READINESS AUDIT

MULTI-CHAIN PAYMENT ENGINE

Esegui una Security & Production Readiness Review completa del Multi-Chain Payment Engine.

REGOLA PRINCIPALE

QUESTO È UN AUDIT STATICO. NON MODIFICARE IL CODICE.

Non implementare fix durante questo step.

Devi analizzare il codice esistente, tracciare i percorsi critici e produrre un report dettagliato con:

* PASS;
* WARNING;
* HIGH;
* CRITICAL;
* eventuali fix necessari.

Dopo il report decideremo separatamente quali correzioni implementare.

⸻

1. USDA — ISOLAMENTO ASSOLUTO

Verificare che il Multi-Chain Engine non abbia introdotto regressioni o dipendenze indesiderate su:

* usda-custodial.service.ts
* USDA wallet management
* USDA scheduler
* USDA payment flow
* chat_transfers
* chat payment
* USDA authentication
* USDA gas flow

Confermare esplicitamente:

USDA ZERO REGRESSIONS / ZERO MODIFICHE FUNZIONALI.

⸻

2. PROJECT FEE 0,10%

Verificare matematicamente e tramite code path che:

projectFee = grossAmount × 10 / 10_000
netAmount = grossAmount - projectFee

rimanga invariata per:

* Polygon USDT;
* Ethereum USDT;
* BSC USDT;
* BTC;
* send_amount;
* recipient_exact.

Verificare che:

networkFeeCharged

NON alteri mai:

projectFee

o:

netAmount.

Verificare inoltre che il fee wallet riceva correttamente la project fee.

⸻

3. RECIPIENT EXACT

Analizzare:

calculatePaymentQuote()

e verificare:

gross = ceil(targetNet × 10_000 / (10_000 - feeBps))

e:

netAmount >= targetNetAmount

Verificare:

* BigInt;
* rounding;
* decimals;
* importi piccoli;
* importi grandi;
* overflow;
* project fee;
* network fee;
* minDepositAmount;
* coerenza tra /quote e create.

La quote preview e la transazione reale devono utilizzare la stessa logica.

⸻

4. NETWORK FEE

Verificare separatamente:

project_fee
network_fee_charged
network_fee_actual

Devono rappresentare tre concetti distinti.

Verificare:

* Polygon → POL;
* Ethereum → ETH;
* BSC → BNB;
* BTC → miner fee.

Verificare che network_fee_charged rimanga immutabile per il transfer dopo la creazione.

Verificare che il cambio successivo dell’ENV non alteri transfer già creati.

⸻

5. EVM PAYOUT — DOUBLE PAYMENT

Analizzare completamente:

TX1 → recipient
TX2 → fee wallet

Verificare tutti i crash point:

A

Crash prima di TX1.

B

TX1 broadcast → crash prima del persist tx_hash_release.

C

TX1 persistita → crash prima di TX2.

D

TX2 broadcast → crash prima del persist tx_hash_fee.

Per ogni scenario stabilire:

* cosa contiene il DB;
* cosa vede lo scheduler;
* quale TX viene eventualmente ritentata;
* se è possibile un double-pay;
* se è possibile una double-fee.

Identificare qualsiasi rischio residuo.

⸻

6. BTC — ATOMICITÀ E DOUBLE SPEND

Analizzare il flusso BTC completo:

deposit
→ UTXO detection
→ UTXO selection
→ PSBT
→ signing
→ broadcast
→ persist
→ confirmation

Verificare:

* TX singola;
* recipient output;
* fee wallet output;
* change;
* miner fee;
* dust;
* UTXO selection;
* deterministic TXID;
* crash prima/dopo broadcast;
* mempool;
* retry;
* refund;
* double broadcast;
* double refund.

Verificare specificamente il rischio:

nuovi UTXO arrivati nell’escrow tra crash e retry.

Classificarlo correttamente.

⸻

7. REFUND SAFETY

Analizzare tutti i percorsi:

pending
→ expired
→ refund

e:

refunding
→ crash
→ recovery

Verificare il caso critico:

→ server crash
→ retry

Analizzare separatamente:

* EVM;
* BTC.

8. WAITING_FOR_GAS

Analizzare completamente il nuovo stato:

Verificare:

* gas insufficiente;
* gas station vuota;
* gas top-up fallito;
* scheduler;
* retry;
* gas_retry_count;
* ritorno a releasing;
* idempotenza;
* alert Admin;

Verificare che:

gas insufficiente NON possa causare perdita del deposito.

Verificare che:

gas insufficiente NON possa modificare project fee o net amount.

Analizzare:

ensureMultiChainEscrowGas()

Verificare:

* POL;
* ETH;
* BNB;
* balance check;
* top-up;
* safety multiplier;

10. SCHEDULER

Audit completo dello scheduler Multi-Chain.

Verificare:

* singleton guard;
* intervalli;

* stale locks;
* releasing;
* refunding;
* waiting_for_gas;
* pending;
* expired;
* feature flags;

* restart;

⸻

11. FEATURE FLAGS

Verificare:

* Polygon;
* Bitcoin;
* Ethereum;
* BSC.

Quando una rete viene disabilitata:

* nessun nuovo transfer deve essere accettato se non previsto;
* transfer già in corso non devono essere corrotti;
* tx_hash_release presente non deve mai essere cancellato;
* nessun rollback distruttivo;
* recovery corretta alla riattivazione.
