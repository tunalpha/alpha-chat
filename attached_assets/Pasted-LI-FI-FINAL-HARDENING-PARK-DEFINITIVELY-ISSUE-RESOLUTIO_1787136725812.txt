FASE 2 — BACKEND AUTHORITATIVE
==================================================

Il browser NON deve mai poter dichiarare autonomamente:

completed
failed
refunded

Per tutti i flussi Li.FI:

- il backend deve conservare il journal/order;
- il backend deve interrogare/verificare Li.FI;
- il backend deve verificare la chain sorgente;
- deve verificare la TX sorgente;
- deve verificare la chain destinazione;
- deve verificare la TX payout quando prevista;
- deve verificare che source TX e payout appartengano allo stesso route/order;
- deve verificare la direzione della route.

Un PATCH dal browser che dichiara "completed" deve essere:
- ignorato;
- rifiutato;
- oppure trattato esclusivamente come evento non autorevole.

MAI deve trasformarsi direttamente in completed.

==================================================

Creare/rafforzare un identificatore server-side unico per ogni swap Li.FI.

- internal swapId;
- provider = "lifi";
- routeId / orderId Li.FI;
- source chain;
- destination chain;
- source asset;
- destination asset;

- destination address;

- source TX hash;
- destination/payout TX hash;
- BTC vault quando applicabile;
- memo/payment reference quando applicabile;
- current authoritative provider status;
- timestamps;
- terminal status.

Tutti history e notification devono essere correlati a questo journal.

NON usare solamente il TX hash come identificatore dello swap.

FASE 8 — NOTIFICHE
==================================================

Implementare notifiche Li.FI idempotenti per:

- swap pending;
- deposito/source transaction rilevata;
- processing/confirming quando significativo;
- completed;
- failed;
- refunded;
- expired.

Regole:

- notification dedup key basata sul journal/swapId + eventType;
- polling ripetuto NON deve duplicare notifiche;
- reload browser NON deve duplicare notifiche;
- retry NON deve duplicare notifiche;

La notifica "completed" deve essere emessa SOLO dopo conferma backend-authoritative.
