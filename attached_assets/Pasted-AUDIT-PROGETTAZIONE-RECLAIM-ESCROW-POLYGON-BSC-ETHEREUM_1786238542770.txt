==================================================
6. SICUREZZA DEL RECLAIM
==================================================

Il reclaim NON deve essere eseguito prima che il payment sia realmente
completato.

Sequenza obbligatoria:

TX1 CONFIRMED
      ↓
TX2 CONFIRMED
      ↓
leggi saldo reale escrow
      ↓
calcola costo TX3
      ↓
verifica saldo sufficiente
      ↓
TX3 RECLAIM
      ↓
attendi/conferma TX3
      ↓
leggi saldo on-chain
      ↓
ESCROW BALANCE ≈ 0
      ↓
RECLAIM COMPLETED

Se TX1 o TX2 non sono confermate:

NON eseguire reclaim.

Il reclaim NON deve mai compromettere un eventuale retry di TX1 o TX2.

==================================================
7. ZERO RESIDUI ABBANDONATI
==================================================

Questo è un requisito fondamentale.

Dopo l'implementazione, nessun escrow EVM completato deve poter rimanere
con native token recuperabili senza essere rilevato.

Il sistema deve avere uno stato dedicato, ad esempio:

RECLAIM_PENDING
RECLAIM_SUBMITTED
RECLAIM_CONFIRMED
RECLAIM_FAILED

Un escrow NON deve essere considerato definitivamente chiuso se contiene
ancora native token recuperabili.

==================================================
8. RECOVERY / SCHEDULER
==================================================

Se TX3 fallisce per:

- RPC timeout;
- RPC unavailable;
- nonce issue;
- gas estimation failure;
- transaction rejected;
- server restart;
- network interruption;
- perdita della risposta RPC;

il payment già completato NON deve fallire.

Il reclaim deve rimanere:

RECLAIM_PENDING / RECLAIM_FAILED

e deve poter essere ritentato automaticamente.

Creare concettualmente un processo:

RECLAIM MONITOR

che periodicamente controlli gli escrow dei payment già completati.

Per ogni escrow:

1. leggere il native balance on-chain;
2. se balance > soglia dust:
   → RECLAIM_PENDING;
3. verificare eventuale TX3 precedente;
4. se nessuna TX3 completata:
   → tentare reclaim;
5. se TX3 già confermata:
   → verificare saldo;
6. se saldo ancora recuperabile:
   → nuovo reclaim controllato;
7. solo quando il saldo è ≈ 0:
   → RECLAIM_CONFIRMED.

Questo controllo deve essere indipendente dal normale flusso del payment.

==================================================
9. IDEMPOTENZA — OBBLIGATORIA
==================================================

Il reclaim deve essere completamente idempotente.

Non deve essere possibile effettuare due reclaim dello stesso saldo.

Gestire correttamente il caso:

TX3 inviata
↓
RPC perde la risposta
↓
scheduler riparte
↓
sistema NON sa se TX3 è stata confermata.

In questo caso:

NON inviare immediatamente una seconda TX.

Prima:

- controllare transaction hash;
- controllare receipt;
- controllare nonce;
- controllare saldo escrow;
- verificare lo stato on-chain.

Solo dopo decidere se è necessario un nuovo reclaim.

==================================================
10. CRASH / RESTART SAFETY
==================================================

Simulare logicamente:

TX1 confermata
TX2 confermata
server crash
TX3 non ancora eseguita

Al riavvio il sistema deve rilevare:

payment completed
+
escrow balance > dust

e mettere automaticamente il reclaim in coda.

Secondo scenario:

TX3 inviata
server crash
TX3 confermata

Al riavvio:

NON effettuare un secondo reclaim.

Terzo scenario:

TX3 fallita

Al riavvio:

RECLAIM_PENDING
→ retry.
