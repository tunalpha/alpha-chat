TASK — ELIMINARE DEFINITIVAMENTE LE NETWORK FEE FLAT E CALCOLARE IL COSTO PER OGNI SINGOLO INVIO

OBIETTIVO

Voglio eliminare completamente le network fee fisse/flat per:

- Polygon
- BSC
- Ethereum

NON voglio più valori commerciali arbitrari come:

- Polygon = 0.01 USDT
- BSC = 0.50 USDT
- BSC = 1.00 USDT
- Ethereum = 15.00 USDT

La network fee deve essere calcolata DINAMICAMENTE PER OGNI SINGOLO INVIO sulla base del costo gas effettivo/realisticamente stimato per quel pagamento.

IMPORTANTE:
Prima ANALIZZA il codice.
NON implementare finché non hai ricostruito esattamente il flusso.
Se trovi ambiguità, fermati e segnalale.

==================================================
1. DISTINZIONE OBBLIGATORIA
==================================================

Devono rimanere due commissioni completamente separate:

A) PROJECT FEE
B) NETWORK FEE

PROJECT FEE:

- default = 0,10%
- DEFAULT_FEE_BPS = 10
- può essere modificata separatamente per ogni rete tramite Admin Panel
- Polygon può avere una percentuale diversa da BSC
- BSC può avere una percentuale diversa da Ethereum
- cambiare una rete NON deve modificare le altre

NETWORK FEE:

NON deve essere una percentuale dell'importo.
NON deve essere un valore flat fisso.
NON deve dipendere dal valore inviato.

Deve rappresentare il costo blockchain del singolo pagamento.

==================================================
2. NETWORK FEE DINAMICA
==================================================

Per ogni singolo pagamento EVM:

1. leggere il gasPrice / fee data LIVE della rete;
2. stimare il gas reale delle operazioni necessarie;
3. considerare tutte le TX necessarie al flusso;
4. calcolare il costo in native token;
5. convertire il costo in USDT usando il prezzo corrente del native token;
6. applicare esclusivamente un eventuale safety margin configurabile;
7. produrre networkFeeCharged specifica per QUEL pagamento.

NON usare:

BSC_FLAT_NETWORK_FEE_USDT
POLYGON_FLAT_NETWORK_FEE_USDT
ETHEREUM_FLAT_NETWORK_FEE_USDT

come network fee del cliente.

Se queste ENV esistono ancora, analizzane l'utilizzo e indicami tutti i punti in cui vengono lette.

NON eliminarle automaticamente senza approvazione.

==================================================
3. COSTO DA CONSIDERARE
==================================================

Analizza il flusso reale attuale.

Gas Station:
TX0 = native token → Escrow

Escrow:
TX1 = USDT → Recipient
TX2 = USDT → Fee Wallet

Dopo il completamento:
TX3 = reclaim native token → Gas Station

Il reclaim TX3 è già implementato.

La network fee dinamica deve essere progettata tenendo conto del costo reale dell'intero ciclo economico.

NON assumere che MC_ANTI_LOSS_GAS_UNITS = costo reale.

NON usare automaticamente 341.000 gas come costo finale.

NON usare 80.000 × 2 × 2 come consumo reale.

Il sistema deve distinguere:

- gas stimato TX0;
- gas stimato TX1;
- gas stimato TX2;
- gas stimato TX3;
- eventuale native token recuperabile dal reclaim;
- costo netto previsto.

==================================================
4. IMPORTANTISSIMO — TX3 RECLAIM
==================================================

Il reclaim avviene DOPO il pagamento.

Quindi analizza attentamente come calcolare la network fee PRIMA della conferma del pagamento.

Voglio una soluzione matematicamente coerente:

NETWORK FEE QUOTATA =
costo gas previsto del ciclo
+
eventuale safety margin

senza trasformare il margine in una fee flat.

Dopo il pagamento:

il sistema deve registrare:

- gasUsed TX0;
- gasUsed TX1;
- gasUsed TX2;
- gasUsed TX3;
- gasPrice effettivo;
- native token consumato;
- native token recuperato;
- costo netto reale;
- networkFeeCharged;
- eventuale differenza tra fee stimata e costo reale.

Questo servirà per il futuro audit economico.

==================================================
7. NESSUN VALORE FLAT
==================================================

Questo requisito è categorico.

NON deve più esistere una logica del tipo:

if BSC:
    networkFee = 0.50

if Ethereum:
    networkFee = 15

if Polygon:
    networkFee = 0.01

La network fee deve cambiare naturalmente in funzione di:

- gas price;
- gas stimato;
- native token price;
- operazioni effettivamente necessarie.

Due transazioni BSC effettuate in momenti diversi possono quindi avere network fee diverse.

Due transazioni Ethereum effettuate in momenti diversi possono avere network fee diverse.

Due transazioni Polygon effettuate in momenti diversi possono avere network fee diverse.

==================================================
9. ANTI-LOSS
==================================================

NON disabilitare anti-loss.

NON modificare:

MC_ANTI_LOSS_GAS_UNITS
waiting_for_gas
fail-closed RPC

senza prima analizzare la compatibilità con la nuova network fee dinamica.

La network fee dinamica serve a calcolare il costo da addebitare al cliente.

L'anti-loss serve a impedire che la piattaforma esegua un pagamento in perdita.

Sono due funzioni diverse.

==================================================
10. FALLBACK E RPC
==================================================

NON inventare un valore.

NON usare una fee flat vecchia come fallback silenzioso.

Il pagamento deve:

- entrare in waiting_for_gas
oppure
- fallire in modo sicuro

secondo la logica fail-closed già esistente.
