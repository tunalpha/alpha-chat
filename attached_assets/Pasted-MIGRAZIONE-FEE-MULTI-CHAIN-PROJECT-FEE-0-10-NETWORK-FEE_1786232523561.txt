MIGRAZIONE FEE MULTI-CHAIN — PROJECT FEE 0,10% + NETWORK FEE

ATTENZIONE:
QUESTA È UNA MODIFICA ECONOMICA CRITICA.

Un errore può causare perdite ad AlphaChat.

NON modificare il codice alla cieca.
Prima analizzare completamente l'implementazione attuale e produrre un report.
Solo dopo l'analisi implementare le modifiche.

==================================================
OBIETTIVO GENERALE
==================================================

AlphaChat applica una PROJECT FEE dello 0,10%.

Il cliente deve inoltre pagare la NETWORK FEE necessaria a coprire il costo della blockchain.

Le due fee devono essere SEMPRE separate.

PROJECT FEE:
- 0,10%
- ricavo AlphaChat
- contabilizzata nel fee ledger
- trasferita al fee wallet secondo il modello di settlement della chain

NETWORK FEE:
- costo della blockchain
- pagata dal cliente
- NON è ricavo AlphaChat
- deve essere sufficiente a coprire il costo blockchain previsto

Il destinatario deve sempre ricevere esattamente l'importo richiesto.

recipient amount

NON ridurre mai l'importo ricevuto dal destinatario.

Gestire correttamente i decimali specifici del token sulla rispettiva chain.

==================================================
PROJECT FEE
==================================================

Project fee:

0,10% = 10 basis points.

La project fee appartiene ad AlphaChat.

Deve essere calcolata in modo identico al comportamento attuale.

NON modificare la percentuale.

NON usare la project fee per coprire il gas.

NON confondere project fee e network fee.

==================================================
NETWORK FEE
==================================================

La network fee viene pagata dal CLIENTE.

Serve a coprire il costo reale della blockchain.

Deve essere calcolata separatamente per ogni chain.

Formula concettuale:

network fee =
costo blockchain stimato
+
buffer ragionevole

Considerare:

- gas estimate
- gas price
- numero di transazioni necessarie
- eventuale top-up BNB/ETH dell'escrow
- buffer configurabile

NON usare valori arbitrari senza prima confrontarli con il costo reale.

==================================================
REGOLA ANTI-PERDITA
==================================================

Prima del pagamento verificare:

networkFeeCharged >= estimatedNetworkCost

Se:

networkFeeCharged < estimatedNetworkCost

NON consentire silenziosamente il pagamento.

Il sistema deve:

- ricalcolare la quote
OPPURE
- aumentare la network fee secondo la configurazione
OPPURE
- bloccare il pagamento indicando che la network fee non è sufficiente.

AlphaChat NON deve assorbire inconsapevolmente il costo della rete.

==================================================
BSC
==================================================

BSC deve utilizzare:

- recipient_exact
- project fee 0,10%
- network fee pagata dal cliente
- fee ledger
- accumulo project fee
- sweep aggregato

NON trasferire la project fee ad ogni pagamento con una TX separata.

Esempio:

Pagamento A → project fee
Pagamento B → project fee
Pagamento C → project fee
Pagamento D → project fee

Tutte:

status = pending

Quando viene raggiunta la soglia configurata:

BSC_FEE_SWEEP_THRESHOLD_USDT

effettuare uno sweep aggregato verso:

BSC_FEE_WALLET

Dopo conferma blockchain:

status = swept

salvare sweep_tx_hash.

==================================================
SWEEP
==================================================

Per BSC ed Ethereum:

NON effettuare una TX fee per ogni pagamento.

Accumularle nel ledger.

Quando la soglia configurata viene raggiunta:

eseguire uno sweep.

Lo sweep deve essere:

- idempotente
- atomicamente protetto
- retryable
- resistente ai crash
- resistente a race condition
- tracciato
- confermato on-chain prima dello stato "swept"

NON creare due sweep contemporaneamente.

NON permettere double payment.
