C-01 — EVM TX1 DOUBLE PAYMENT

Problema:

TX1 broadcast
↓
crash prima di persist tx_hash_release
↓
scheduler rollback/retry
↓
TX1 nuovamente inviata

Questo è un GO-LIVE BLOCKER.

Obiettivo

Eliminare il rischio di doppio invio di TX1.

Preferire una soluzione realmente idempotente, non una semplice riduzione della finestra temporale.

Soluzione preferita

Separare:

1. costruzione della transaction;
2. firma;
3. persistenza dello stato/hash;
4. broadcast;
5. receipt confirmation.

Il sistema deve poter conoscere il transaction hash deterministico della TX firmata prima del broadcast.

Persistire uno staging state/hash prima di effettuare il broadcast.

Esempio concettuale:

build TX
↓
sign TX
↓
txHash deterministico
↓
persist tx_hash_release + stato broadcast_pending
↓
broadcast
↓
confirmation
↓
released / continue TX2

Se il processo crasha dopo il broadcast ma prima della receipt:

tx_hash_release != null

il recovery deve verificare lo stato on-chain e NON costruire una nuova TX1.

NON utilizzare un semplice “try/catch” come meccanismo di idempotenza.

⸻

C-02 — EVM TX2 DOUBLE FEE

Applicare lo stesso principio alla TX2.

Attualmente:

TX2 broadcast
↓
crash
↓
tx_hash_fee non persistito
↓
retryEVMFeeTx
↓
TX2 duplicata

Eliminare questo rischio.

La TX2 deve avere:

build
→ sign
→ deterministic txHash
→ persist staging hash
→ broadcast
→ confirmation
→ final DB state

Se tx_hash_fee esiste:

NON inviare una nuova TX2.

Verificare prima on-chain:

* pending;
* confirmed;
* failed/replaced;
* not found.

Il recovery deve agire diversamente a seconda dello stato.

⸻

C-03 — DOUBLE REFUND

Il refund deve diventare idempotente come il payout.

Gestire separatamente:

Caso A

Errore prima del broadcast:

NO tx broadcast
→ rollback/retry consentito

Caso B

Broadcast effettuato:

txHash disponibile
→ persist hash
→ crash
→ recovery
→ verifica on-chain
→ NON creare un secondo refund

Aggiungere, se necessario:

tx_hash_refund

e/o uno staging status appropriato.

Applicare il principio:

dopo che una TX può essere stata broadcastata, il sistema non deve mai assumere che non sia stata inviata solo perché non ha ricevuto una risposta.

Questo vale sia per EVM sia per BTC dove applicabile.

⸻

H-01 — REFUND STUCK LOCK

Spostare la balance query del refund dentro una gestione try/catch completa.

Qualsiasi eccezione durante:

* getBalance;
* getTokenBalance;
* adapter call;
* RPC;

non deve lasciare permanentemente:

status = refunding
locked_at = ...

Aggiungere recovery scheduler per eventuali refunding stale.

La recovery deve essere idempotente.

NON fare rollback cieco se esiste già un tx_hash_refund.

⸻

H-02 — OWNERSHIP VALIDATION

Aggiungere controllo ownership per:

* GET transfer;
* detect;
* release;
* refund.

Un utente deve poter operare solo sui propri transfer.

Utilizzare il campo effettivamente presente nell’authenticated request.

Il controllo deve essere eseguito lato backend e NON affidarsi al frontend.

Admin routes devono mantenere le proprie autorizzazioni Admin.

Aggiungere test:

User A → transfer A → allowed
User A → transfer B → 403/404
User B → transfer A → 403/404

Non rivelare informazioni sul transfer al proprietario errato.

⸻

H-03 — GAS STATION KEY

GAS_STATION_PRIVATE_KEY mancante NON deve essere un warning che permette al payout di proseguire.

Deve essere una configurazione non valida per le reti che richiedono gas station.

Comportamento:

missing key
↓
configuration error
↓
NO TX payout
↓
transfer recuperabile

NON esporre mai il nome del secret o il suo contenuto al cliente.

Aggiungere startup/config validation dove appropriato.

ATTENZIONE:

Non bloccare USDA se la configurazione Multi-Chain manca.

La validazione deve essere isolata al Multi-Chain Engine.
