Certo. Questo è il prompt che darei a Power, aggiungendo BTC ↔ Lightning come provider obbligatorio nella V1, ma mantenendo tutto completamente isolato.

ALPHA SWAP V1 — LI.FI + BTC/LIGHTNING

OBIETTIVO

Procedere con l’implementazione completa del modulo Alpha Swap, mantenendolo totalmente isolato dalla payment logic esistente.

La V1 deve avere due integrazioni provider:

PROVIDER 1 — LI.FI

Responsabile di:

* swap EVM;
* cross-chain;
* asset/reti supportati da LI.FI;
* Bitcoin on-chain quando la route LI.FI lo supporta.

PROVIDER 2 — BTC/LIGHTNING

Responsabile esclusivamente di:

* BTC Mainnet → BTC Lightning;
* BTC Lightning → BTC Mainnet.

Il provider BTC/Lightning deve essere scelto verificando prima la documentazione ufficiale e la disponibilità di:

* submarine swap;
* reverse submarine swap;
* API;
* quote;
* monitoring;
* gestione degli stati;
* supporto non-custodial;
* possibilità di applicare una fee integrator/partner/affiliate.

NON scegliere un provider BTC/Lightning arbitrariamente.

Prima dell’integrazione verificare quale provider soddisfa meglio questi requisiti e riportare la scelta.

⸻

1. ARCHITETTURA

Creare un’astrazione comune:

SwapProvider

con adapter separati:

LiFiSwapProvider

BitcoinLightningSwapProvider

La UI NON deve conoscere quale provider sta eseguendo lo swap.

Esempio:

BTC → BTC Lightning

→ routing interno
→ BitcoinLightningSwapProvider

E:

USDT → USDC

→ routing interno
→ LiFiSwapProvider

⸻

2. REGOLA ASSOLUTA — ZERO REGRESSIONI

NON MODIFICARE LA PAYMENT LOGIC ESISTENTE.

Sono completamente fuori scope:

* invio BTC on-chain esistente;
* ricezione BTC;
* UTXO selection esistente;
* BTC fee logic esistente;
* RBF;
* Lightning payment logic già esistente;
* USDT transfer;
* USDC transfer;
* ETH transfer;
* POL transfer;
* WalletConnect;
* ThirdWeb;
* firma delle transazioni esistenti;
* polling esistente;
* deposit detection;
* escrow;
* payment history;
* balance logic esistente.

Se una parte dello Swap richiede una modifica alla payment logic:

FERMATI. NON MODIFICARLA. Segnala il conflitto.

Lo Swap deve essere completamente isolato.

⸻

3. ASSET

Lo Swap deve utilizzare gli asset già presenti/supportati da Alpha.

NON creare manualmente ogni coppia.

Il sistema deve permettere:

Asset A → Asset B

quando esiste una route supportata.

Esempi:

* USDT → USDC
* USDC → ETH
* ETH → POL
* POL → USDT
* BTC → ETH
* BTC → USDT
* BTC → BTC Lightning
* BTC Lightning → BTC

Se non esiste una route:

Swap non disponibile per questa coppia

NON mostrare quote inventate.

⸻

4. USDA

USDA deve essere temporaneamente esclusa SOLO dal modulo Swap.

Configurazione:

SWAP_EXCLUDED_ASSETS = ["USDA"]

USDA:

* NON deve apparire nel selettore Swap;
* NON deve essere quotabile nello Swap;
* NON deve essere modificata o rimossa dal wallet;
* deve continuare a funzionare normalmente nelle sue funzioni esistenti.

L’esclusione deve essere configurabile, così in futuro USDA può essere riattivata senza modifiche strutturali.

⸻

5. FEE ALPHA

Fee iniziale:

0,25% = 25 BPS

Configurazione centralizzata:

ALPHA_SWAP_FEE_BPS = 25

NON hardcodare la fee in più punti.

La fee deve essere configurabile dall’Admin.

L’Admin deve poter modificare:

* Alpha Fee BPS;
* treasury recipient;
* Swap ON/OFF;
* asset esclusi;
* provider ON/OFF.

La fee deve essere applicata lato backend/provider, non affidata solamente al frontend.

⸻

6. FEE SEPARATE

Mostrare separatamente:

* Alpha Fee;
* Provider Fee;
* Network Fee;
* Bridge Fee, quando presente;
* Slippage;
* Importo stimato ricevuto.

Non sommare tutto sotto una voce generica.

L’utente deve sapere chiaramente quanto paga ad Alpha.

⸻

7. LI.FI

Usare LI.FI come provider principale per le route che supporta.

Utilizzare la modalità ufficiale di integrator fee.

L’integrator deve essere configurabile:

alpha-wallet

La fee deve essere applicata tramite i meccanismi ufficiali LI.FI.

NON alterare manualmente transaction data BTC o dati raw forniti dal provider.

API key/segreti/treasury NON devono essere esposti nel frontend.

⸻

8. BTC ↔ LIGHTNING

Implementare il secondo provider come adapter separato.

Deve supportare:

BTC Mainnet → Lightning

Submarine swap.

Lightning → BTC Mainnet

Reverse submarine swap.

Il flusso deve essere:

Quote

→ Confirm

→ Payment/Firma

→ Submitted

→ Pending

→ Completed

oppure:

Failed

Expired

Cancelled

Il provider deve essere selezionato solo dopo verifica della documentazione ufficiale.

NON implementare un protocollo Lightning proprietario.

NON custodire le chiavi private degli utenti.

⸻

9. BTC/LIGHTNING FEE

Verificare se il provider BTC/Lightning scelto supporta una fee per integrator/partner.

Obiettivo:

Alpha Fee configurabile anche sugli swap BTC ↔ Lightning.

Se il provider supporta la fee:

applicare la stessa configurazione Alpha:

ALPHA_SWAP_FEE_BPS

Se il provider NON supporta una fee nativa:

NON creare workaround non documentati.

Segnalare il limite prima del deploy.

⸻

10. ROUTING

Creare un router interno:

SwapRouter

→ BitcoinLightningSwapProvider

→ BitcoinLightningSwapProvider

→ LiFiSwapProvider

Il router deve essere estendibile.

ZeroXSwapProvider

senza riscrivere UI o state management.
