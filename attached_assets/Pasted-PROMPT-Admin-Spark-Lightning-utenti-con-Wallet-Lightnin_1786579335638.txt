PROMPT — Admin Spark/Lightning: utenti con Wallet Lightning abilitato

OBIETTIVO

Migliorare esclusivamente la sezione Admin → Spark / Lightning Monitor.

Attualmente la pagina mostra:

"Utenti con Spark abilitato"
"Il tracking per-utente Spark non è disponibile lato server..."

Questo non è sufficiente.

Voglio che l'Admin possa vedere chiaramente QUANTI utenti hanno abilitato Spark/Lightning e, se tecnicamente possibile senza modificare il core dei pagamenti, quali utenti lo hanno abilitato.

IMPORTANTE:
NON modificare il funzionamento del wallet Spark.
NON modificare Breez SDK.
NON modificare Alpha Wallet.
NON modificare Payment Engine.
NON modificare BTC on-chain.
NON modificare Signal/Chat.
NON modificare USDA.
NON modificare fee Spark esistenti.
NON modificare il sistema di invio/ricezione Lightning.
NON aggiungere userId ai fee records esistenti se questo richiede modifiche al core Spark.

La modifica deve essere limitata al tracking amministrativo dell'abilitazione Spark.

--------------------------------------------------
1. REGISTRO UTENTI SPARK
--------------------------------------------------

Creare un meccanismo server-side separato per registrare l'abilitazione Spark di un utente.

Quando un utente abilita Spark/Lightning, registrare almeno:

- userId
- stato: enabled / disabled
- createdAt
- updatedAt
- lastSeenAt, se facilmente disponibile
- eventuale wallet Spark identifier NON sensibile, solo se già disponibile e sicuro

NON salvare:
- mnemonic
- seed
- private key
- PIN
- segreti Breez
- dati sensibili del wallet.

Creare una collection separata, ad esempio:

spark_user_status

con indice unico su userId.

Se esiste già un meccanismo equivalente nel progetto, riutilizzarlo invece di crearne uno duplicato.

--------------------------------------------------
2. QUANDO REGISTRARE L'UTENTE
--------------------------------------------------

Il record deve essere creato/aggiornato quando Spark viene effettivamente abilitato per l'utente.

IMPORTANTE:

"Feature flag globale ON" NON significa che l'utente abbia Spark abilitato.

Distinguere chiaramente:

A) Spark globale disponibile
B) Utente con Spark configurato/abilitato
C) Utente effettivamente connesso a Spark

L'Admin deve poter distinguere questi stati.

Non considerare un utente "Spark enabled" semplicemente perché il feature flag globale è true.

--------------------------------------------------
3. ADMIN — CARD TOTALI
--------------------------------------------------

Nella pagina:

Admin → Spark / Lightning Monitor

aggiungere card reali:

⚡ UTENTI SPARK
Numero totale utenti con Spark abilitato.

🟢 ATTIVI
Utenti Spark con stato attivo/abilitato.

🔴 DISABILITATI
Utenti che hanno disabilitato Spark, se il dato è disponibile.

💸 MOVIMENTI LIGHTNING
Numero totale dei movimenti Spark già presenti nei fee records.

Non inventare numeri.

Se non ci sono dati mostrare 0.

--------------------------------------------------
4. SEZIONE "UTENTI CON SPARK ABILITATO"
--------------------------------------------------

Sostituire l'attuale messaggio:

"Il tracking per-utente Spark non è disponibile lato server"

con una vera tabella/lista.

Colonne desiderate:

- Utente
- Stato Spark
- Data abilitazione
- Ultima attività
- Movimenti
- Ultimo movimento

Esempio:

⚡ Utente123
🟢 Attivo
13/08/2026 22:10
13/08/2026 22:41
5 movimenti
13/08/2026 22:41

Se alcuni dati non sono disponibili, mostrare "N/D".

NON inventare dati.

--------------------------------------------------
5. PRIVACY
--------------------------------------------------

L'Admin deve vedere solamente le informazioni necessarie per la gestione del servizio.

NON mostrare mai:

- mnemonic
- seed
- private key
- PIN
- credenziali Breez
- dati crittografici
- segreti del wallet.

Se il sistema utilizza username/display name, preferire quello all'ObjectId MongoDB.

Se non esiste username disponibile, utilizzare un identificatore amministrativo già previsto dal sistema.

--------------------------------------------------
6. MOVIMENTI
--------------------------------------------------

NON modificare alpha_wallet_fee_records.

NON aggiungere userId ai fee records esistenti solo per ottenere questo risultato.

Per associare i movimenti all'utente, utilizzare il nuovo registro separato o una relazione già esistente nel database.

Se una relazione affidabile non esiste, NON fare associazioni speculative.

In quel caso:

Movimenti totali → dato aggregato reale.

Movimenti per singolo utente → N/D.

--------------------------------------------------
7. SICUREZZA ADMIN
--------------------------------------------------

Tutte le nuove API devono essere protette come le attuali API Spark Monitor.

Accesso:

read_only admin → può visualizzare i dati.

super_admin → può visualizzare e gestire.

Nessun utente normale deve poter accedere alle API amministrative.

Validare userId lato server.

Non esporre dati sensibili.

--------------------------------------------------
8. API
--------------------------------------------------

Creare endpoint dedicati, ad esempio:

GET /api/v1/spark/monitoring/users

GET /api/v1/spark/monitoring/users/stats

oppure adattarsi alle convenzioni già presenti nel progetto.

L'endpoint deve restituire solo dati necessari al monitor.

Implementare:

- paginazione
- eventuale filtro enabled/disabled
- ordinamento per lastSeenAt o createdAt
- conteggio totale

Non fare query inefficienti sull'intera collection ad ogni caricamento.
