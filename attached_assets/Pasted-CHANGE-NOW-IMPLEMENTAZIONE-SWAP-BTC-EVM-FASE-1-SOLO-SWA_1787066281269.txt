FLUSSO
Implementare un adapter/service isolato con flusso:

1. verifica pair/availability
2. quote/rate
3. create exchange
4. ricezione deposit address BTC
5. restituzione exchange/order ID
6. l'utente firma e invia BTC dal proprio Alpha Wallet
7. backend salva lo stato dell'operazione
8. polling ChangeNOW Transaction Status
9. attendere stato finale verificabile
10. ottenere destination transaction hash
11. SOLO con prova verificabile della destination transaction → completed
12. in caso di refund → mantenere lo swap in stato appropriato e registrare le informazioni restituite da ChangeNOW

CRITICO — FUNDS COMMITTED
Una volta che il BTC è stato effettivamente inviato al deposit address ChangeNOW:

fundsCommitted = true

Da quel momento:
- NON cambiare provider
- NON creare un secondo exchange
- NON generare un nuovo deposit address
- NON reinviare BTC
- NON fare fallback automatico
- NON tentare un secondo send

Se lo stato è incerto dopo l'invio BTC:
→ pending/recovery
→ polling/status recovery
→ MAI double-send.

DESTINATION TX
NON considerare completed semplicemente perché ChangeNOW restituisce uno stato generico di successo.

Richiedere una prova verificabile:
- stato finale appropriato
- destination transaction hash presente

Se destination transaction hash è assente:
→ NON completed
→ continuare recovery/polling secondo policy.

BTC TX ≠ DESTINATION TX:
Il txid Bitcoin utilizzato per il deposito NON deve mai essere registrato come destination EVM transaction hash.

- NON effettuare un nuovo send
- recuperare l'exchange esistente
- interrogare ChangeNOW
- continuare il monitoraggio
- aggiornare lo stato fino alla conclusione.
